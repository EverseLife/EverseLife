# Выкладка альфы

Как поднять everse.life на сервере, выдать ему настоящий сертификат и настроить
выкладку с GitHub. Порядок написан для чистой Ubuntu 24.04 и домена вида
`alpha.example.com`, но на любом другом дистрибутиве с Docker всё то же самое.

## Из чего состоит боевой состав

`deploy/compose.yaml` поднимает восемь служб плюс пять наблюдающих:

| служба | что делает |
| --- | --- |
| `postgres` | база. Порты наружу не публикует: в неё ходят по внутренней сети состава |
| `migrate` | накатывает схему (`alembic upgrade head`) и завершается. Сервер стартует только после него |
| `seed` | заводит стартовый мир и догоняет его до сегодняшнего устройства, затем завершается. Идёт при каждой выкладке; сервер стартует после него |
| `backend` | сервер игры: чтение по `/public/*`, сессия игрока по `/session/ws` |
| `worker` | доводит долгие дела: тик мира, партии, дороги, счета за быт. **Без него мир стоит** |
| `frontend` | nginx с собранным клиентом |
| `landing` | лендинг с приёмом заявок на бету, свой домен (`LANDING_DOMAIN`). Заявки — SQLite на томе `landing_data`, в базу игры не ходит |
| `agents` | панель ИИ-граждан (D-224), свой домен (`AGENTS_DOMAIN`). Агенты играют через `/session/ws` бэкенда; их журнал — SQLite на томе `agents_data` |
| `caddy` | граница: TLS, сертификат Let's Encrypt, маршруты `/` → клиент и `/api/*` → сервер; лендинг — отдельным доменом |

`backend`, `worker` и `migrate` — один и тот же образ: расходиться версиями им
нельзя. Числа игры запекаются в образ при сборке: прогон берёт их из вольта
(`EverseLife/EverseLifeVault`), а какие именно — видно в `/api/health`
отпечатком констант.

Клиент собран без боевого домена внутри: он ходит на тот же источник, откуда
открыт, на путь `/api`. Один образ годится любому домену.

Ещё пять служб — `node-exporter`, `cadvisor`, `postgres-exporter`, `prometheus`
и `grafana` — смотрят за самим сервером и наружу не выведены; про них отдельно
в разделе «Мониторинг».

## Что нужно

* сервер: от 2 ядер и 4 ГБ памяти, 20 ГБ диска. На двух ядрах сервер идёт
  одним процессом и держит около сотни человек одновременно, на шести —
  четырьмя процессами и вдвое больше; почему так, ниже в «Сколько людей
  выдержит». Число процессов надо назвать в `.env` самому
  (`EVERSELIFE_WEB_WORKERS`), по числу ядер оно не подберётся. Диска мало не
  будет: мир на тысячу аккаунтов весит 15 МБ, растёт в нём журнал событий;
* домен и A-запись на адрес сервера (`alpha.example.com` → `203.0.113.10`);
* открытые снаружи порты **80 и 443**. Порт 80 нужен не для игры, а для выдачи
  сертификата: без него Let's Encrypt не подтвердит домен;
* Docker с плагином compose.

## Сколько людей выдержит

Числа ниже сняты `backend/tools/loadtest.py` — это не расчёт, а замер: тот же
образ, что едет на сервер, весь состав прижат к шести логическим ядрам, база
своя, а клиенты играют настоящий распорядок — `look` раз в пять секунд, как
шлёт браузер. Хорошо — пока p95 ответа держится ниже 500 мс.

| Настройка | Одновременно | Команд/с | p95 на потолке |
| --- | --- | --- | --- |
| один процесс, пул 5+10 — как было до этой настройки | ~150 | ~30 | 507 мс |
| четыре-шесть процессов, пул 10+5 | ~300 | ~60–75 | 909 мс на 350 |

Главное, что из этого следует: **лишние ядра сами по себе не помогают.** Без
`--workers` сервер — это один Python под замком интерпретатора, и потолок в 150
человек стоял одинаково и на шести ядрах, и на тридцати двух. Всё, что даёт
переход на четыре процесса, — ровно вдвое; дальше упирается снова, но уже не в
ядра.

Пересчёт в живых людей делается не по числу подключений, а по числу команд:
праздный клиент шлёт 0,2 команды в секунду, занятый (пока идёт партия, дорога
или добыча) — 0,5. Поэтому шестьдесят команд в секунду — это либо три сотни
людей, стоящих по своим делам, либо полторы сотни работающих. Считать стоит по
худшему.

Что при этом **не** ограничивает:

* **вебсокеты.** Четыреста живых соединений не уронили ни одного и заняли
  490 МБ на шесть процессов. Соединение почти ничего не стоит; стоит то, что
  оно спрашивает каждые пять секунд;
* **база.** Постгрес на потолке занят на треть одного ядра из шести. Один
  `look` — это около сотни запросов, но сама база тратит на них доли
  миллисекунды: время уходит на сто последовательных обращений из Python. Пока
  это так, ни pgbouncer, ни реплика ничего не изменят;
* **диск и память.** 15 МБ на тысячу аккаунтов, 490 МБ памяти на шесть
  процессов.

Дороже всего в игре стоит пошлина устройства (D-110): `mine.start` — 109 мс, и
две с половиной таких в секунду съедают около целого ядра, потому что сервер
считает Argon2id ровно того же веса, что и клиент. Это осознанная цена, а не
поломка, но при расчёте запаса её надо держать в уме: сотня шахтёров дороже
сотни торговцев.

Оговорка про стенд: замеры сняты на десктопном процессоре, ядра которого
быстрее облачных vCPU примерно в полтора раза. **На обычном VPS ждите от этих
чисел 60–75%** — то есть около двух сотен одновременных на шести ядрах с
настройками из `.env.example` и около сотни, если оставить один процесс.
Повторить замер на своём железе стоит до того, как позовёте людей:
как — написано в шапке `backend/tools/loadtest.py`. Гонять его по бою нельзя:
регистрация печатает настоящие тела в мир, который не вайпается (D-007), — для
этого поднимается копия состава.

Когда потолка перестанет хватать, порядок такой: сначала `EVERSELIFE_WEB_WORKERS`
по числу ядер минус два (воркеру и базе нужно своё), затем ядра, и только
потом — сокращать сотню запросов в `look`. Последнее даёт больше всего, но это
уже работа по движку, а не по выкладке.

## Один раз: подготовка сервера

```bash
# от root
apt update && apt upgrade -y
curl -fsSL https://get.docker.com | sh

# отдельный человек для игры, чтобы не жить под root
adduser --disabled-password --gecos "" everselife
usermod -aG docker everselife

# Пароля у него нет, значит нужен ключ — иначе к нему не подключиться.
# Проще всего отдать тот же, которым вы ходите root'ом.
install -d -m 700 -o everselife -g everselife /home/everselife/.ssh
cp /root/.ssh/authorized_keys /home/everselife/.ssh/authorized_keys
chown everselife:everselife /home/everselife/.ssh/authorized_keys
chmod 600 /home/everselife/.ssh/authorized_keys

mkdir -p /opt/everselife
chown everselife:everselife /opt/everselife
```

Проверить, что дверь открылась, — со своей машины:

```powershell
ssh -i $env:USERPROFILE\.ssh\<ваш ключ> everselife@alpha.example.com "docker version --format '{{.Server.Version}}'"
```

`scp` и `ssh` берут только ключи с именами по умолчанию (`id_ed25519`,
`id_rsa`), поэтому свой указывайте явно через `-i` — либо опишите сервер раз и
навсегда в `~/.ssh/config`:

```
Host everselife
  HostName alpha.example.com
  User everselife
  IdentityFile ~/.ssh/<ваш ключ>
```

Брандмауэр — только то, что нужно:

```bash
ufw allow OpenSSH
ufw allow 80/tcp
ufw allow 443/tcp
ufw --force enable
```

Дальше всё от пользователя `everselife`.

Положить на сервер состав и настройки. Файлы `compose.yaml` и `Caddyfile`
лежат в репозитории (`deploy/`), и дальше их будет привозить выкладка; в первый
раз проще скопировать руками со своей машины:

```powershell
# из корня репозитория, на своей машине
scp deploy/compose.yaml deploy/Caddyfile deploy/.env.example everselife@alpha.example.com:/opt/everselife/
```

На сервере сделать из образца настоящий `.env`:

```bash
cd /opt/everselife
mv .env.example .env
# придумать пароль базы
openssl rand -base64 32
nano .env      # DOMAIN, ACME_EMAIL, POSTGRES_PASSWORD, GHCR_OWNER
chmod 600 .env
```

`.env` живёт только на сервере и в репозиторий не попадает: в нём пароль базы.
Выкладка его не трогает.

## Один раз: образы

Образы собирает CI и кладёт в GitHub Container Registry. Чтобы сервер мог их
забрать, нужен доступ. Два пути:

1. **сделать пакеты открытыми** — GitHub → репозиторий → Packages →
   `everselife-backend` → Package settings → Change visibility → Public. Тогда
   сервер тянет образы без пропуска, а выкладке ничего не нужно объяснять;
2. **входить по пропуску** — создать токен с правом `read:packages` и один раз
   выполнить на сервере `docker login ghcr.io -u <логин>`.

Выкладка из CI входит в реестр сама, своим одноразовым пропуском, — оба
варианта нужны только для запусков руками.

## Первый запуск

Сначала CI должен собрать образы: толкнуть ветку `main` и дождаться зелёного
прогона (`Actions` → `CI`). Дальше на сервере:

```bash
cd /opt/everselife
docker compose pull
docker compose up -d
docker compose ps
```

Руками не нужно ничего: до старта сервера отрабатывают две одноразовые службы —
`migrate` накатывает схему, `seed` заводит столицу и догоняет мир до сегодняшнего
устройства. Обе идут при **каждом** подъёме состава, то есть при каждой выкладке.

Почему сид живёт службой, а не миграцией: миграция применяется один раз в
истории базы, а стартовый мир меняется вместе с вольтом — это содержимое, а не
схема (`catch_up` в `src/seed_catchup.py`). Повторный запуск ничего не создаёт дважды:
каждый шаг сначала смотрит, есть ли уже сделанное.

Если сид почему-то упал, сервер не поднимется — так и задумано: пустой или
недоделанный мир хуже явной остановки. Смотреть, что случилось:

```bash
docker compose logs seed
```

Проверка:

```bash
curl https://alpha.example.com/api/health
# {"ok":true,"constants":"<отпечаток>"}
```

Отпечаток в ответе — те самые числа вольта, на которых работает сервер. Открыть
`https://alpha.example.com` — должен подняться клиент и завестись сессия.

## SSL

Сертификатом занимается Caddy, и это весь ответ: он сам получает его у
Let's Encrypt по протоколу ACME и сам продлевает за месяц до конца срока.
Никакого certbot, никакого задания в cron, никакой перезагрузки по расписанию.

Что для этого должно совпасть:

1. `DOMAIN` в `.env` — тот самый домен, которым игроки открывают игру;
2. A-запись домена указывает на адрес сервера. Проверить: `dig +short
   alpha.example.com` должен вернуть адрес сервера;
3. порт **80** доступен снаружи. Через него идёт подтверждение владения
   доменом (HTTP-01). Закрыть его «потому что весь трафик по 443» — самая
   частая причина, по которой сертификат не выдаётся;
4. `ACME_EMAIL` — живая почта: туда придёт письмо, если с продлением беда.

Что происходит при первом запуске: Caddy видит домен в `Caddyfile`, идёт за
сертификатом, кладёт его в том `caddy_data` и включает HTTPS. Заодно он сам
отправляет всех с `http://` на `https://`. Том переживает пересоздание
контейнера — у Let's Encrypt есть предел на число выдач для одного домена
(пять штук в неделю), и терять уже выданное при каждой выкладке нельзя.

Посмотреть, как прошло:

```bash
docker compose logs caddy | tail -50
```

Строка `certificate obtained successfully` — всё получилось. Если вместо неё
ошибки подтверждения, разбираться по порядку: DNS доехал? порт 80 открыт
снаружи (`curl http://alpha.example.com` с другой машины)? домен в `.env`
совпадает с тем, что в DNS?

Пока настройка не устоялась, лучше пробовать на **испытательном** удостоверяющем
центре: его сертификату браузер не поверит, зато пределов на выдачу там
практически нет. Добавить в начало `deploy/Caddyfile`, в общий блок:

```
{
	email {$ACME_EMAIL}
	acme_ca https://acme-staging-v02.api.letsencrypt.org/directory
}
```

Как получилось — строку убрать, выполнить `docker compose up -d --force-recreate
caddy` и получить настоящий сертификат.

Проверить срок и цепочку снаружи:

```bash
echo | openssl s_client -connect alpha.example.com:443 -servername alpha.example.com 2>/dev/null | openssl x509 -noout -dates -issuer
```

### Если нужен именно nginx с certbot

Caddy заменяем, порядок такой: поставить `nginx` и `certbot` на сам сервер
(`apt install nginx certbot python3-certbot-nginx`), убрать службу `caddy` из
состава, опубликовать наружу порты клиента и сервера только на петлю
(`127.0.0.1:8080:80` у `frontend`, `127.0.0.1:8000:8000` у `backend`) и положить
в `/etc/nginx/sites-available/everselife`:

```nginx
server {
    listen 80;
    server_name alpha.example.com;

    location /api/ {
        proxy_pass http://127.0.0.1:8000/;
        proxy_http_version 1.1;
        # Сессия игрока — сокет: без этих двух заголовков она не поднимется.
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        # Игрок может молчать в сокет часами: короткий срок оборвёт сессию.
        proxy_read_timeout 3600s;
    }

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
    }
}
```

Дальше `ln -s` в `sites-enabled`, `nginx -t && systemctl reload nginx` и
`certbot --nginx -d alpha.example.com`: certbot сам перепишет блок под 443 и
заведёт продление таймером systemd (`systemctl list-timers | grep certbot`).
Проверить продление вхолостую: `certbot renew --dry-run`.

## CI/CD

Всё живёт в `.github/workflows/ci.yml` и идёт одной цепочкой:

1. **Сервер** — окружение по замку `uv.lock`, `ruff`, `alembic upgrade head` на
   чистой базе, полный `pytest` (~8 минут). База поднимается службой прогона;
2. **Клиент** — `npm ci`, `oxlint`, сборка;
3. **Образы** — только с `main`: собираются и уезжают в GHCR под двумя метками,
   `latest` и отпечаток коммита;
4. **Выкладка** — только с `main`: привозит на сервер `compose.yaml` и
   `Caddyfile`, тянет образы, поднимает состав и стучится в `/api/health`.

На запросах слияния идут первые два шага: на сервер уезжает только то, что
прошло тесты.

### Что завести на GitHub

Settings → Secrets and variables → Actions.

Секреты:

| имя | что это |
| --- | --- |
| `DEPLOY_HOST` | адрес или домен сервера |
| `DEPLOY_USER` | `everselife` |
| `DEPLOY_SSH_KEY` | закрытый ключ выкладки целиком, вместе со строками `BEGIN`/`END` |
| `DEPLOY_PORT` | порт SSH, если не 22 (необязательно) |
| `DEPLOY_KNOWN_HOSTS` | строка из `ssh-keyscan` для сервера (необязательно, но лучше завести) |
| `DISCORD_DEPLOY_WEBHOOK` | вебхук канала выкладок в Discord (необязательно; без него шаг молчит) |

Переменные (вкладка Variables):

| имя | значение |
| --- | --- |
| `DEPLOY_ENABLED` | `true` — пока её нет, выкладка молчит |
| `DEPLOY_PATH` | `/opt/everselife` (необязательно) |
| `DEPLOY_DOMAIN` | `alpha.example.com` — по нему проверяется, что сервер ожил |

Ключ выкладки — отдельный, не тот, которым вы сами ходите на сервер:

```bash
# на своей машине
ssh-keygen -t ed25519 -f deploy_key -N "" -C "github-deploy"
ssh-keyscan alpha.example.com     # это в DEPLOY_KNOWN_HOSTS
```

`ssh-copy-id` в Windows нет, поэтому открытую половину доливаем строкой:

```powershell
type deploy_key.pub | ssh everselife@alpha.example.com "cat >> ~/.ssh/authorized_keys"
```

Содержимое `deploy_key` (закрытая половина) — в `DEPLOY_SSH_KEY`, после чего
файл с машины стереть.

### Откат

Образы помечены отпечатком коммита, так что вернуться к прошлой сборке — дело
одной строки на сервере:

```bash
cd /opt/everselife
sed -i 's/^TAG=.*/TAG=<отпечаток коммита>/' .env
docker compose pull && docker compose up -d
```

Схему это не откатывает: миграции вперёд, откат — отдельным решением.
Возвращаясь на `latest`, не забыть вернуть строку обратно.

## ИИ-граждане (панель агентов)

Панель агентов (`agentic_player_system/`, D-224) едет так же: CI собирает образ
`everselife-agents` из корня репозитория (в образ замораживается
`backend/src/api/commands/` той же ревизии — из докстрингов `@command` собирается
справочник команд для модели), выкладка поднимает службу `agents`. Агенты ходят в `backend` по внутренней
сети, как обычные игроки. Наружу панель не смотрит, пока на сервере не сделано:

1. A-запись `agents.everse.life` → адрес сервера;
2. в `/opt/everselife/.env`: `AGENTS_DOMAIN=agents.everse.life`,
   `AGENTS_ADMIN_PASSWORD=...` (единственный вход в панель; игровой роли
   «админ» нет) и `AGENTS_LLM_API_KEY=...` (ключ DeepSeek или другого
   OpenAI-совместимого провайдера; его же можно ввести в панели — тогда
   значение из панели главнее);
3. там же `AGENTS_SECRET_KEY=...` — им запечатываются игровые пароли агентов и
   ключ провайдера в базе панели. Без него они лежат открытым текстом, и копия
   тома — это они же. Ключ делается так:

   ```bash
   docker compose run --rm --no-deps agents python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
   ```

   Меняется ключ перечислением через запятую: новый первым, старый следом, пока
   панель не перепишет всё (перепечатывает при сохранении);
4. `docker compose up -d --force-recreate caddy agents` — Caddy возьмёт сертификат.

Агенты, журнал и ключ, введённый в панели, живут в SQLite на томе `agents_data`.
Остановить всех разом — выключить каждого в панели или `docker compose stop agents`.

## Лендинг

Лендинг (`landing/`) едет тем же путём, что и всё остальное: CI собирает образ
`everselife-landing`, выкладка поднимает службу. Наружу он не смотрит, пока на
сервере не сделано один раз:

1. A-запись голого домена (`example.com`) → адрес сервера;
2. `LANDING_DOMAIN=example.com` в `/opt/everselife/.env`;
3. `docker compose up -d --force-recreate caddy` — Caddy возьмёт сертификат.

`www.` — отдельное имя: ему нужна своя запись (A или CNAME на голый домен —
ACME хватит того, что имя резолвится сюда) и свой сертификат. Блок
`www.{$LANDING_DOMAIN}` в `Caddyfile` вечным редиректом уводит на голый домен;
без него Caddy рвёт TLS-рукопожатие вместо ответа, и каждая ссылка с `www.`
мертва.

Поисковикам о сайте надо сказать: Google — только через Search Console, а Bing
и Yandex принимают уведомление по IndexNow. Для него в `.env` кладётся
`LANDING_INDEXNOW_KEY` (`python -c "import secrets; print(secrets.token_hex(16))"`),
после чего служба отдаёт `/{ключ}.txt`, а уведомление шлётся вручную, когда
страницы правда изменились:

```bash
docker compose exec landing python indexnow.py
```

Заявки на бету копятся в SQLite на томе `landing_data`. Забрать:

```bash
cd /opt/everselife
docker compose exec landing python export.py > signups.csv
```

Подробности — в [landing/README.md](landing/README.md).

## Лендинг на отдельном хосте — запасной путь

**Так сейчас не развёрнуто.** Лендинг живёт на игровом хосте, службой `landing`
в основном `compose.yaml`, и едет обычной выкладкой; `LANDING_DEPLOY_ENABLED`
выключён, джоб `deploy-landing` молчит. Раздел оставлен готовым порядком
действий на случай, если адрес снова начнёт фильтроваться.

Переезд пробовали 1 сентября 2026 и в тот же день отменили. Затевали его ради
доступности из РФ: адреса Contabo фильтруются частью российских домашних сетей
по спискам, которых никто не публикует, а лендинг — воронка, страница,
обязанная открываться у незнакомца. Отменили потому, что выбранный ради
досягаемости адрес (Timeweb Cloud Amsterdam) оказался под тем же ТСПУ-фильтром:
смена хостера досягаемости не покупает, и это подтвердили два провайдера и три
адреса подряд. Если v4-доступность из РФ понадобится всерьёз, дешевле не менять
хостера, а поставить трубу — VPS в РФ, TCP-проходом на origin.

Файлы переезда живые и рабочие, а лендинг для такого разделения и построен:
своя SQLite на своём томе, в игровую базу — ни одного запроса. Игра при переезде
остаётся на прежнем хосте (записи `alpha.` и `agents.` не трогаются), пока новый
адрес не докажет себя.

Хост выбирается по одному критерию — досягаемость из российских домашних
сетей. Проверка кандидата до оплаты и после выдачи адреса:

```bash
python tools/subnet_watch.py <адрес>
```

Чистота по публичным спискам необходима, но недостаточна (фильтры по
хостерским диапазонам не публикуются), поэтому после переключения DNS
единственная настоящая проверка — люди из РФ в Discord.

Порядок на чистой Ubuntu (докер и пользователь — как в «Один раз: подготовка
сервера», это умеет cloud-init):

1. `mkdir -p /opt/everselife-landing`, туда — `deploy/compose.landing.yaml`,
   `deploy/Caddyfile.landing` и `.env` c `LANDING_DOMAIN` и `ACME_EMAIL`
   (по желанию — `LANDING_DISCORD_WEBHOOK`, `LANDING_INDEXNOW_KEY` со старого
   `.env`).
2. Образ. Правильный путь — сделать пакет `everselife-landing` в GHCR
   публичным (страница пакета → Package settings → Change visibility):
   репозиторий и так публичный, а тянуть образы без токенов сможет любой
   хост. Тогда шаг сводится к `docker compose pull`. Пока пакет приватный —
   перекинуть файлом. Только не через пайп между двумя `ssh`: PowerShell
   перекодирует поток как текст и портит бинарные данные, поэтому каждый
   бинарник едет через `scp`, а не через `|`:

   ```bash
   ssh СТАРЫЙ "docker save ghcr.io/everselife/everselife-landing:latest | gzip > /tmp/landing.tgz"
   scp СТАРЫЙ:/tmp/landing.tgz .
   scp landing.tgz НОВЫЙ:/tmp/
   ssh НОВЫЙ "gunzip < /tmp/landing.tgz | docker load && rm /tmp/landing.tgz"
   ```

3. Заявки. Тот же принцип — файлом через `scp`:

   ```bash
   ssh СТАРЫЙ "docker run --rm -v everselife_landing_data:/data -v /tmp:/out alpine cp /data/signups.db /out/signups.db"
   scp СТАРЫЙ:/tmp/signups.db .
   scp signups.db НОВЫЙ:/tmp/
   ssh НОВЫЙ "docker volume create everselife-landing_landing_data && docker run --rm -v everselife-landing_landing_data:/data -v /tmp:/src alpine cp /src/signups.db /data/signups.db && rm /tmp/signups.db"
   ```

   Имена томов — от имени папки состава; при сомнении `docker volume ls`.
   Порядок важен: сначала том, потом `up`, иначе новые заявки разъедутся по
   двум базам, и их придётся сливать экспортом.
4. `docker compose -f compose.landing.yaml up -d`. По 443 до переключения DNS
   проверить нечего: ACME HTTP-01 не пройдёт, пока имя не смотрит сюда, а без
   сертификата Caddy не завершает рукопожатие вовсе (`-k` не спасает — ему
   нечего предъявить). Дым проверяется по 80-му порту, редиректом от Caddy:
   `curl --resolve $LANDING_DOMAIN:80:<адрес> -sI http://$LANDING_DOMAIN/` —
   ответ `308` значит, что кромка стоит и маршрут жив.
5. Сразу после переключения DNS — `docker compose -f compose.landing.yaml
   restart caddy`: неудачные попытки ACME копят задержку повтора, и без
   рестарта сертификат может прийти на минуты позже, чем DNS.
6. DNS: A и AAAA голого домена → новый хост. `www` уедет CNAME'ом сам, свой
   сертификат Caddy выпишет в первую минуту после переключения. Записи
   `alpha.` и `agents.` остаются на игровом хосте — обе, включая AAAA.
7. Секреты Actions для автоматической выкладки: `LANDING_DEPLOY_HOST`,
   `LANDING_DEPLOY_USER`, при нестандартном порте `LANDING_DEPLOY_PORT`,
   отпечаток в `LANDING_DEPLOY_KNOWN_HOSTS`; ключ — тот же `DEPLOY_SSH_KEY`
   (его публичная половина — в `authorized_keys` нового хоста). Переменные:
   `LANDING_DEPLOY_ENABLED=true`, `LANDING_DOMAIN` — для проверки «ожил».
   До этого шага джоб `deploy-landing` молчит, и правки лендинга едут только
   руками.
8. Мониторинг перенастраивать не нужно: `subnet-watch` проверяет каждое имя
   по тому адресу, куда смотрит DNS, — с переключением он сам начнёт
   сторожить новый хост, а игровые имена — прежний.

Откат — вернуть записи голого домена на игровой хост. Если на новом успели
накопиться заявки, слить их: `export.py` с обоих, объединить, залить файл
обратно шагом 3.

Блок `{$LANDING_DOMAIN}` в основном `Caddyfile` при этом не трогается: DNS
уводит трафик, и блок просто перестаёт отвечать. Убирать его стоит только
вместе с переездом игры, если он случится.

## Если у состава меняется имя

Имя состава (`name:` в `compose.yaml`) — то, из чего Docker выводит имена томов.
Переименовали проект — и `everselife_pgdata` это уже **другой**, пустой том;
старый `octoverse_pgdata` остаётся лежать рядом нетронутым. То же самое с
сертификатами Caddy и заявками лендинга. Плюс Postgres в новом томе ждёт роль с
новым именем, которой в старых данных нет.

Отсюда две дороги.

**Начать с нуля** — если мир не жалко (на альфе это обычный случай). Заодно
меняется и пользователь: раз имя проекта другое, `octoverse` на сервере тоже ни
к чему. Всё, что ему принадлежало, — каталог состава и ключи, и то и другое
заводится заново. От root:

```bash
adduser --disabled-password --gecos "" everselife
usermod -aG docker everselife

# ключи переезжают как есть: и ваш, и ключ выкладки
install -d -m 700 -o everselife -g everselife /home/everselife/.ssh
cp /home/octoverse/.ssh/authorized_keys /home/everselife/.ssh/authorized_keys
chown everselife:everselife /home/everselife/.ssh/authorized_keys
chmod 600 /home/everselife/.ssh/authorized_keys

mkdir -p /opt/everselife && chown -R everselife:everselife /opt/everselife
```

Старый состав отпускает порты 80 и 443 и уходит:

```bash
cd /opt/octoverse && docker compose down
```

Настройки переезжают с новыми именами ключей — от root, потому что `.env` читает
только его владелец:

```bash
sed -e 's/^OCTOVERSE_/EVERSELIFE_/' -e 's/^GHCR_OWNER=.*/GHCR_OWNER=everselife/' /opt/octoverse/.env > /opt/everselife/.env
chown everselife:everselife /opt/everselife/.env
chmod 600 /opt/everselife/.env
```

И секрет `DEPLOY_USER` на GitHub становится `everselife`: иначе выкладка
постучится к пользователю, которого больше нет.

Дальше обычный прогон — выкладка привезёт состав в новый каталог, `migrate`
накатит схему, `seed` заведёт мир. Когда всё поднимется, старое убрать:

```bash
docker volume rm octoverse_pgdata octoverse_caddy_data octoverse_caddy_config octoverse_landing_data
sudo deluser --remove-home octoverse
```

**Перенести данные** — если мир нужен. Порядок такой: снять снимок
(`pg_dump -Fc`), остановить службы, держащие соединения, переименовать базу
(`ALTER DATABASE`) и роль (её переименовывает **другой** суперпользователь:
себя Postgres переименовать не даёт), скопировать каждый том в том с новым
именем через промежуточный контейнер, перенести каталог и ключи `.env`, поднять
состав. Пароль это переживает: с Postgres 14 он хранится как scram и от имени
пользователя не зависит.

## Переезд на другой домен

Домен нигде не зашит в образы: клиент ходит на тот же источник, откуда открыт,
а Caddy берёт имена из `.env`. Поэтому переезд — это записи в DNS и три строки
настроек, без пересборки.

1. **DNS нового домена**: A-запись голого имени (`example.com`) и A-запись
   игры (`alpha.example.com`) — обе на адрес сервера. Проверить:
   `nslookup -type=A alpha.example.com 8.8.8.8`;
2. **`.env` на сервере** — `DOMAIN`, `LANDING_DOMAIN` и, если старый домен
   остаётся указателем, `LEGACY_DOMAINS` (через запятую):

```bash
cd /opt/everselife
nano .env
docker compose up -d
```

   `up -d` пересоздаст `caddy` (новые сертификаты) и `backend` с `worker` — им
   от домена достаётся разрешённый источник сессии;

3. **переменная `DEPLOY_DOMAIN` на GitHub** — по ней выкладка проверяет, что
   сервер ожил. Не поправить — прогон будет краснеть на последнем шаге, стуча
   в старый адрес.

Старый домен не бросайте сразу: ссылки на него уже разошлись по Discord и
приглашениям. Пока его A-записи смотрят сюда, `LEGACY_DOMAINS` держит его
указателем — Caddy отвечает на нём постоянным перенаправлением на лендинг.
Строку убирают, когда старые ссылки перестают быть нужны.

Что до текстов: адрес попадается в страницах лендинга — русских в `landing/` и
английских в `landing/en/` (в том числе `og:url`, который видит превью ссылки в
Discord, и ссылки `hreflang`, которыми языки указывают друг на друга), в
`community/discord.md` и в парочке описаний. Это правится в репозитории и
доезжает обычной выкладкой.

Почты стартовых Тэрна и Хёма (`FOUNDERS` в `src/seed_parts.py`) — **логины живых
учёток**. Правка в коде их не переименует: догон назначает почту только тем, у
кого её нет. Либо оставить как есть — домен в логине никуда не ходит, — либо
менять из кабинета руками.

## Discord

Четыре ленты наружу: хроника мира из воркера, счётчик заявок из лендинга, итог
выкладки из CI и тревоги сервера из Grafana. У каждой **свой** вебхук и свой
канал — `EVERSELIFE_DISCORD_WEBHOOK`, `LANDING_DISCORD_WEBHOOK` и
`GRAFANA_DISCORD_WEBHOOK` в `/opt/everselife/.env`, секрет
`DISCORD_DEPLOY_WEBHOOK` на GitHub. Пока их нет, всё молчит и ничего не
ломается.

Тревоги отделены намеренно: их канал закрытый, а утёкший или отозванный вебхук
не должен глушить хронику вместе с собой.

Порядок и проверка — в [community/discord-bridge.md](community/discord-bridge.md),
устройство сервера сообщества — в [community/discord.md](community/discord.md).

## Числа игры

Числа, рецепты и законы правятся **только в вольте**
(`github.com/EverseLife/EverseLifeVault`, файлы `data/*.yaml`). Слепка в этом
репозитории нет: `vault/*.json` — вывод сборки, и он собирается в прогоне.

Работы «Server» и «Images» первым делом клонируют вольт, гоняют его
`tools/build.py` и кладут пять файлов в `vault/` — числа, рецепты, законы,
растения и раскладку стартового мира (D-243): тесты считают мир по ним,
образ сервера забирает их внутрь. Синхронизировать руками нечего, следить не за
чем — числа всегда те, что лежат в вольте на момент прогона.

Отсюда порядок, и он намеренный: **пуш в вольт сам по себе ничего не меняет на
альфе**. Чтобы новые числа уехали, нужен прогон в репозитории игры — обычный
пуш либо `Actions → CI → Run workflow`. Правка баланса не должна трогать живой
мир, пока её никто не позвал.

Локально числа берутся тем же сборщиком:

```bash
python deploy/sync-vault.py
```

Он пересоберёт вольт по соседству и положит результат в `vault/`. В коммит эта
папка не попадёт — она в `.gitignore`; и это же значит, что собрать образ
сервера руками можно только после неё, иначе `COPY vault /vault` копировать
нечего.

Какие именно числа работают на сервере, видно в `/api/health` отпечатком
констант — сверять с прогоном по нему.

## Эксплуатация

```bash
cd /opt/everselife

docker compose ps                       # кто жив
docker compose logs -f backend worker   # что происходит
docker compose restart worker           # мир встал — начинать отсюда
docker compose exec postgres psql -U everselife -d everselife
```

Снимок базы (мир вечный, вайпов не бывает — снимки не роскошь):

```bash
docker compose exec -T postgres pg_dump -U everselife -Fc everselife > ~/everselife-$(date +%F).dump
```

Вернуть из снимка:

```bash
docker compose stop backend worker
docker compose exec -T postgres pg_restore -U everselife -d everselife --clean --if-exists < ~/everselife-2026-08-14.dump
docker compose start backend worker
```

Ежедневный снимок в cron у пользователя `everselife` — пять минут работы и
единственное, что отделяет альфу от потери мира:

```
0 4 * * * cd /opt/everselife && docker compose exec -T postgres pg_dump -U everselife -Fc everselife > ~/backup/everselife-$(date +\%F).dump && find ~/backup -name '*.dump' -mtime +14 -delete
```

## Мониторинг

За сервером смотрит свой стек в том же составе: **node-exporter** (процессор,
память, свободное место, сеть), **cAdvisor** (каждый контейнер отдельно),
**postgres-exporter** (соединения, размер базы), **Prometheus** (собирает и
хранит) и **Grafana** (панели и тревоги). Наружу не смотрит ничего: экспортёры
портов не публикуют вовсе, Grafana слушает только петлю сервера.

Пятый источник — сам **лендинг**: он считает свою посещаемость и отдаёт её на
`/metrics`, задание `landing` в `deploy/prometheus.yml` забирает её по имени
службы через сеть состава. Наружу этот адрес не выведен: Caddy отвечает на
`/metrics` 404, и отдельного пароля поэтому нет. Что там считается и почему
своим счётчиком, а не чужим скриптом — [landing/README.md](landing/README.md),
раздел «Аналитика».

Обходится это примерно в 150 МБ памяти сразу после запуска; Prometheus дальше
подрастает вместе с историей — глубина задаётся `PROMETHEUS_RETENTION`
(по умолчанию 15 дней, это порядка гигабайта диска).

### Как посмотреть

Наружу Grafana не выведена намеренно, поэтому туннель со своей машины:

```powershell
ssh -i $env:USERPROFILE\.ssh\<ключ> -L 3000:localhost:3000 everselife@<сервер>
```

Пока сессия открыта, панель живёт на `http://localhost:3000`. Вход — `admin` и
пароль из `GRAFANA_ADMIN_PASSWORD` в `/opt/everselife/.env`; не задан — `admin`,
и это стоит поправить. Панелей две, обе в папке `everse.life`: «Сервер альфы» —
про железо и базу, «Лендинг» — про людей (визиты, источники, метки `utm_*`,
устройства, воронка до заявки). Обе заводятся файлом: правки в интерфейсе не
сохраняются, потому что источник истины — `deploy/grafana/dashboards/server.json`
и `deploy/grafana/dashboards/landing.json`.

### Тревоги

Четыре, и все о том, после чего мир останавливается:

| тревога | когда |
| --- | --- |
| Место на диске кончается | меньше 15% на самом полном разделе, десять минут подряд |
| Память под потолком | занято больше 90% четверть часа |
| База не отвечает | `pg_up` ноль пять минут |
| Служба перезапускается | больше трёх перезапусков за полчаса — падает, а не выкладывается |

Молчание метрик тревогой не считается: пропал сборщик — это дыра в наблюдении,
а не беда в мире, и во время выкладки такие пропуски бывают у всех служб сразу.
Плата за это честная: если сервер умрёт целиком, тревоги не придут — придёт
тишина, и заметить её можно по красному прогону выкладки либо глазами.

Уходят они в Discord — вебхук в `GRAFANA_DISCORD_WEBHOOK`. Пока переменной нет,
подставляется заведомо мёртвый адрес: тревоги срабатывают и видны в интерфейсе,
но никуда не летят. Пустую строку туда писать нельзя — Grafana откажется
стартовать на канале без адреса, а служба наблюдения не должна ронять выкладку.

### После первой выкладки стоит проверить

Настройки Prometheus и Grafana привозит выкладка (`deploy/prometheus.yml` и
`deploy/grafana/` едут вместе с `compose.yaml`), но `.env` — по-прежнему руками.
И один раз стоит убедиться, что cAdvisor видит контейнеры, а не один корневой
срез:

```bash
cd /opt/everselife && docker compose logs cadvisor --tail 5
```

Строки `Failed to create existing container` означают, что ему не хватает
доступа к `/var/lib/docker`; на обычном Linux-сервере со штатными монтированиями
такого не бывает, но проверить дешевле, чем однажды обнаружить пустые панели.

Выключить наблюдение целиком, если оно вдруг мешает:

```bash
cd /opt/everselife && docker compose stop grafana prometheus cadvisor node-exporter postgres-exporter
```

## Что в альфе честно не сделано

* **Опознание — почта и пароль без подтверждения почты** (D-187): письма
  никто не шлёт, восстановление пароля — через саппорт руками. Стартовым
  Тэрну и Хёму сид назначает тестовые учётки (`FOUNDERS` в `src/seed_parts.py`);
  на уже живом мире их выдаёт **догон**, а он идёт службой `seed` при каждой
  выкладке — руками запускать ничего не нужно.
  **На бою пароли сменить из кабинета в первый же день.** Закрытую альфу
  по-прежнему разумно прикрыть дверью на границе: в `deploy/Caddyfile` для
  этого заготовлен блок `basic_auth`;
* **сокет не проверяет источник.** CORS закрывает чтение чужому домену, но на
  соединение сессии он не распространяется;
* **воркер один.** Их можно поднять сколько угодно (`docker compose up -d
  --scale worker=2`), задания разбираются без координации, но альфе хватит
  одного;
* **метрик наружу нет** — только журналы служб;
* **снимки базы не делаются сами**, пока не заведёте задание выше.
